# 公開前の点検から改稿まで

Suikoの方針は「日本語文書を決定的に診断し、自然で明晰な推敲を支援する」です。同じ入力・バージョン・設定に同じ診断を返し、指摘の位置と理由を原文で確かめられるようにします。指摘を採用するかは、読み手と文脈に照らして判断します。

原稿が一通りできたら、公開・共有する前に、初見の読者が説明を追えるかを確かめます。書き手が隣で補足しなくても、何を伝えたいのか、何を判断してほしいのかが分かる状態に整えます。Suikoで読み直す箇所を絞り、指摘の前後を読んで直し、もう一度診断するのが基本の手順です。

## 点検する目的と機能

| 原稿で困っていること | 使う機能 | 結果を読んで判断すること |
|---|---|---|
| どこから読み直せばよいか分からない | `lint`の行・抜粋・理由と`reading_load` | 何を指し、何をするか。長い文や列挙で読み手が保持する情報を減らせるか |
| 説明が行き来し、結論が見えない | `outline` | 前提・根拠・結論の順序が対象読者に合うか |
| 用語を知っている前提で書いてしまう | `terms`、複数ファイルでは`terms --audit` | 初出の説明が読者に十分か。同じ対象を別の表記で呼んでいないか |
| 修正を共有し、同じ指摘の往復を減らしたい | `--baseline`、理由付きの個別許可、独自ルール、CI出力 | 指摘が消えた理由と、意図して残す理由。プロジェクトの方針に合うか |
| 提出ファイルにも同じ内容を保ちたい | `academic`とDOCX/PDFの照合 | 論証・引用・本文・書式が記録した提出方針と一致するか |

## 公開前の一巡

1. 読者と、読み終えた後に分かること・できることを一文で書き留める。
2. `suiko lint draft.md --genre tech --json > before.json` で初回の診断を保存する。
3. 指摘された行の前後を読み、事実と意味を保って直すか、残す理由を記録する。
4. `suiko lint draft.md --genre tech --baseline before.json --json` で変化を確認する。
5. 通読し、読者の判断に必要な対象・条件・動作が本文から分かるか確かめる。

ジャンルは原稿に合わせ、不要なら省きます。追加の表現候補を見るときは両方の診断に`--experimental`を付けます。比較には同じSuikoのバージョン、ジャンル、実験機能の指定、設定、ファイル名を使います。v0.3.10以前の診断JSONはv0.3.11のbaselineには使えないため、更新後に初回の診断を保存し直します。

`resolved`は検出条件に一致しなくなったという結果です。意味が改善したかは原文との比較で確認します。`persisting`も意図して残せます。`reading_load`はbaselineに含まれないため、今回の出力を読み直します。判断が終わり、事実と意図が保たれたら完了とします。

## 意味の補完を読者へ押し付けていないか

書き手は、原稿に書かなかった事情も知っています。その記憶で理由や条件を補いながら読むと、説明の抜けを見つけにくくなります。「意味は分かる」と感じたら、本文から分かったのか、自分の経験でつないだのかを確かめます。

たとえば「指摘を確認してから公開する」だけでは、すべて直すのか、必要なものを選ぶのかが決まりません。Suikoでは指摘の前後を読み、直すか、残す理由を記録します。短い名詞句の直後の読点も、強調に必要なら残せます。この判断を手順に書くことで、確認を任された人は、指摘件数をゼロにする必要があるのかと迷わずに済みます。

説明を増やせばよいわけでもありません。想定読者が知っている用語や、前段で説明した対象は省略できます。補うのは、省くと結論や次の行動が変わる情報です。書き足す前に原稿や参照資料を探し、根拠が見つからなければ著者へ確認します。未決の判断は未決と書き、もっともらしい理由で埋めません。

### 表現ごとに確かめること

| 読み直す箇所 | v0.3.11の対応 | 改稿で確認すること |
|---|---|---|
| 対象を曖昧な呼び方で受け、比喩的な動詞で説明する | `abstract_metaphor`等は限定した形を扱う。指示対象の省略全般は未検出 | 比較する対象と、判断を変える条件を書く |
| 採否を方向として表す | `decision_direction_metaphor`を追加。全ジャンルの実験機能 | 採否の条件と、残す・除外する等の実際の動作を書く。前後で十分に説明済みなら残す |
| 短い否定から肯定へつなぎ、対象や条件を省く | 既存`negative_listing`は否定2文からの型、`antithesis_repetition`は明示的対比の反復に限定。意味のつながりは判定しない | 否定した方法と次に選ぶ方法の関係を確かめ、必要な理由を補う |
| 動作の順序を反転した対句で効果を曖昧にする | 順序の妥当性や効果の実在は未検出 | 方法ごとの違いと、何が改善するのかを書く。実測のない効果を補わない |
| 短い名詞句の直後に読点を置く | `short_object_comma`を追加。既存`short_topic_comma`と共通の形態素処理を使う | 読点を外して読み、述語とのつながりを確かめる。強調や読みやすさに必要なら残す。曖昧な主語は別に確認する |

新しい2カテゴリは`info`の確認候補で、自動修正は付きません。短い表現でも、前後から対象と判断が分かるなら残せます。省略と説明不足の見分け方は、[改稿ガイド](../skills/suiko/references/revision-guide.md)の同名の節で詳しく扱います。

## チームで使うときの完了条件

CIの`--fail-on`は選んだ重要度以上の指摘があるかを判定します。文章全体の合格判定ではありません。誤字、事実、引用の正確さ、書き手の経験の真偽は別の確認が必要です。チームでは、読者が迷った箇所、その修正、残した表現の理由をレビューします。必要な語や反復を指摘回避のためだけに言い換えないようにします。

今後の機能追加は、実際に読者が困った例と似た自然な例を対にして評価します。対象範囲を示すこと、理由から次の修正を判断できること、意味を壊さないことを確認します。現在のラベル付き評価は検出条件の検証であり、人の改稿時間や読解成績が改善したという証拠ではありません。検出条件と再測定は[校正記録](../eval/calibration.md)に残します。
