# 6軸をSuikoの形態素解析へ落とす検討

調査日: 2026-09-06。出発点はNatural Japaneseの[6軸評価基準](https://github.com/coji/natural-japanese/blob/9a78a42964096da509b8f3e011f0085a5f080151/skills/natural-japanese/references/eval-rubric.md)。競合全体の比較は[別紙](competitive-review-2026-09-06.md)に記録した。

6軸の一部は機能にできる。ただし、点数を出す6個の検出器には分けない。各軸を確かめるための「位置付きの観測」を作り、意味を判断する必要があるところは文脈の確認へ渡す。1件の指摘が複数軸に関係しても、重ねて減点しない。

## Suikoでの6軸

| 元の軸 | Suikoで確認すること | 形態素で拾う手掛かり | 追加で必要な情報 | 機械化の範囲 |
|---|---|---|---|---|
| 1. 文体の自然さ | 同じ表現の型が局所的に繰り返されるか | 基本形、助詞列、活用、文末、数詞と助数詞 | 同じ段落・節での反復、引用の除外 | 既存検出を拡張できる。定型であることと不自然であることは区別する |
| 2. 情報密度 | 説明の予告や抽象的な動作名が内容を圧迫していないか | 本節等の文書指示語、説明・紹介等のサ変名詞、形式的な述語 | 段落頭、節内の反復、既存指摘との重複 | 予告の反復や冗長候補は可能。同義の言い換えや新情報の有無は判定しない |
| 3. 情報の見つけやすさ | 読者が条件と操作をたどれるか | 条件節の末尾、命令・依頼、対象の名詞、用語の初出 | 見出し、手順ブロック、コード、前後の段落、想定読者 | 条件と操作の候補位置を出せる。読者が迷うかは別途確認する |
| 4. 論理と根拠 | 比較・効果の主張に何が添えられているか | 改善・削減等の述語、程度語、数詞と単位、比較助詞 | 同じ指標、比較対象、前後の説明、表・出典 | 根拠の手掛かりを示せる。因果の正しさ、数値の真偽は判定しない |
| 5. 人間味・誠実さ | 観測、推測、伝聞、書き手の判断が区別されているか | 過去形、観測動詞、推量表現、引用の「と」、一人称 | 引用の範囲、文章の目的、素材の出典 | 記述形式の観測に限定する。実体験の有無や誠実さを点数にしない |
| 6. 自己証明力 | 文書内の明示した説明と実際の構造が合うか | 項目数の宣言、列挙を指す名詞・助数詞 | 直後のリストの階層と項目数、明示された文書方針 | 項目数の不一致は可能。文章全体の説得力は判定しない |

形態素解析は語の境界と文法上の手掛かりを返す。主語・述語の対応や否定の作用範囲が、そのまま得られるわけではない。実装では「同じ節と断定」せず、距離、助詞、句読点、文書境界で候補を限定し、それでも残る曖昧さを説明する。

## 実際の分かち書きで確認したこと

[23文の探索用入力](six-axis-morphology-probe.txt)を、既存の`Morphology::tokenize`で実行した。SudachiDict core 20260723、Mode C。これは検出器の精度評価ではなく、設計した条件を形態素で表現できるかの確認である。試作のトークン表示プログラムは作業用領域で実行し、本体へ追加していない。

| 表現 | 観測した形 | 設計への影響 |
|---|---|---|
| 本節では…説明します | 本節 / で / は / … / 説明（サ変可能）/ し（する）/ ます | 文書指示語と述語の組を候補にできる |
| …について説明しました | に / つい（つく）/ て / 説明 / し / まし / た | 「について」が一語になる前提は使えない。過去の説明行為を予告と混同しない |
| 大幅に改善しました | 大幅（形状詞）/ に（助動詞「だ」）/ 改善（サ変可能）/ し / まし / た | 「に」を助詞だけに限定すると見落とす |
| 30%改善しました | 30（数詞）/ %（助数詞可能）/ 改善 | 数字だけでなく単位まで見る必要がある |
| 2025年に…大幅に改善しました | 2025（数詞）/ 年（助数詞可能）/ … / 改善 | 年号の存在を改善量の裏付けとみなしてはいけない |
| 再実行してください | 再実行（普通名詞・一般）/ し / て / ください（くださる・命令形） | 動作名をサ変可能だけに限定すると落ちる |
| 復旧できます／できません | 復旧 / でき（できる）/ ます、または ませ / ん（ぬ） | 可能と否定を別々に観測できる |
| 復旧する必要があります | 復旧 / する / 必要 / が / あり（ある）/ ます | 「ある」だけで肯定とせず、義務を表す組を維持する |
| 次の3点／確認事項は三つ | 次 / の / 3（数詞）/ 点（助数詞可能）、三（数詞）/ つ（接尾辞・助数詞） | 数詞の判定に加え、助数詞の品詞差と漢数字の処理が必要 |

「私は昨日…測定しました」と「…測定しました」は、どちらも観測行為の過去形を持つ。一方、「私は昨日…測定したと書いてください」も途中まで同じ形を持つ。一人称と過去形の有無だけで、経験や誠実さを判定する案は成立しない。

## 最初の機能候補: 宣言した項目数とリストの不一致

6軸目を、主観的な説得力から検証可能な自己整合へ狭める。次の文書なら「3点とあるが、直後のリストは2項目」と位置付きで示せる。

```markdown
以下の3点を確認してください。

- 接続先
- 認証情報
```

既存の`outline`を実行すると、1行目の先頭文と3行目の「箇条書き 2 項目」が別々に抽出された。必要な材料の一部は既にあるが、この対応関係を検査する機能はない。

最小の条件案:

1. リスト直前の段落で、`次の／以下の + 数詞 + 点／項目／つ`等の限定した宣言を拾う。文中の最初の数字を使わず、列挙対象の助数詞に結びつく数字を使う。
2. 次の構造ブロックがリストの場合だけ、同じ階層の項目数と比較する。別見出し、本文段落、引用を越えて探さない。
3. 入れ子の子項目を親の件数へ足さない。リスト項目内の複数段落やコードを別項目として数えない。
4. 宣言対象が曖昧な文、「全10項目のうち次の3点」、省略記号、複雑なリスト形式は、初期版では判定しない。
5. 初期版は構造を確実に数えられるMarkdownだけを対象にした実験的な`info`とし、自動で数字や本文を直さない。

出力文の案: 「3点と予告していますが、直後の箇条書きは2項目です。項目の不足か、予告の数字を確認してください。」

既存の`OutlineEntry`は項目数を表示用文字列へ含めており、この文字列を解析し直す設計は避ける。構造走査中の数を内部で受け渡すか、既存のリスト走査を再利用できるか確認する。現在の`flush_block`はリストらしい行を数えるため、入れ子や項目内コードをそのまま正しい件数とみなせない。

受け入れ例: 3対2を検出、3対3を除外、親3件と子2件を3件として扱う、`3秒以内に次の2点`を2件として扱う。初期対応する数字表記とマークアップを明示し、扱えない形を推測しない。

これは「理由は3つ」を禁止する機能ではない。数を先に示す有用な文章を残し、実際に読み手を迷わせる不一致だけを扱える点で、Suikoに向いている。

## 次の候補: 説明を予告する文の反復

2軸目の「情報密度」を、語彙多様性や文字数の代わりに、内容を予告する同じ型の繰り返しから調べる。

候補の形は、段落頭の文書指示語（本節、本章等）と、説明・紹介・解説等の動作名、`する`系の述語の組。単発では報告しない。同じ節内で反復するかを集計し、作業予告を内容の説明へ変えられる箇所として指す。

出力文の案: 「この節では、説明を予告する文が3回あります。予告が必要な箇所と、そのまま説明を始められる箇所を確認してください。」

形態素の基本形で「説明します」「説明する」を束ねつつ、時制と文頭を保つ。「担当者が説明しました」の過去の出来事は除外する。「説明しない」「説明できる」まで同じ予告として束ねない。

限界: 教材の各章に1回ずつ置く案内、議事録の予定、目次、操作手順は必要な場合がある。集計は文書全体でなく節に閉じる。3回は試験用の候補閾値であり、採用済みの基準ではない。

既存の`repeated_sentence_lead`と`self_labeling_repetition`と重なれば、同一箇所の修正を二重に促さない。既存の反復集計を再利用し、ジャンル別・文書種別別のラベルで追加価値を確かめる。

## 根拠や条件は「欠落判定」より「照合材料」にする

3・4軸目は、文だけを読んで欠落を断定すると誤検出が増える。

- `必要に応じて + 操作 + してください`から、条件の確認先を探す候補は作れる。ただし、直前の表で条件を定義しているかもしれない。現行の散文マスクでは表の内容を除くため、表を見ずに「条件がない」と報告できない。
- `程度語 + 改善／削減`から、何がどの程度変わったかを確認する候補は作れる。ただし、数詞があれば裏付け済みともいえない。年号、版番号、比較と無関係な件数を除き、単位と指標の対応を見る必要がある。
- `AよりB`や`AからBへ`を拾っても、比較条件が公平か、因果関係があるかは分からない。参照先の表や出典を読まなければならない。

最小案はSkillが確認すべき文と周辺を選ぶ補助。CLIの警告として追加するなら、文脈付きの評価を先に行う。単独の曖昧語を増やすだけなら、既存textlint併用との差が小さい。

## 5軸目は「人間らしさ」を数えない

形態素で扱えるのは、観測動詞と過去形、推量、伝聞、判断の表現などの分布である。これを「根拠の示し方の確認材料」として提示することは考えられる。しかし、一人称の密度や感情語の数を品質へ換算すると、自然な技術報告を不当に低く評価する。

また、書き手の体験を本当に確認するには元資料が必要になる。存在しない経験を加える改稿を高く評価しない。「判断を保留した文」「誰の観測か示した文」を残せたかは、改稿前後の評価で扱う。

## 横断的な候補: 改稿による意味変化の確認

形態素解析を、最終稿の診断だけでなく原稿との照合にも使う。今回の例では、同じ「復旧」に対して、`できる`、`ぬ`、`する必要がある`を区別できた。改稿でこれらが消えたら、対応する文を人が確認する価値がある。

ただし、否定の数だけを比較してはいけない。「できないわけではない」から「場合によってはできる」への改稿では、否定が減っても慎重な肯定を保てる。逆に「必ず成功する」から「成功する」では、否定の数が同じでも確実性が変わる。

最小案は、同じ述語を持つ対応文に限ってモダリティの変化を調べる評価用の試作。文の分割・結合や述語の言い換えで対応が不明なら、結果を出さない。「意味が変わった」と断定せず、「可能表現がなくなったので確認する」と説明する。利用価値が確認できるまで、新CLIや保存形式を作らない。

## 実装順と採用の条件

1. **項目数の不一致**: 読者への具体的な支障と正解が明確。形態素とMarkdown構造の組み合わせを最初に試す。
2. **説明予告の反復**: 既存の形態素と反復処理を再利用できる。誤検出と既存指摘の重複を測ってから採用する。
3. **改稿前後の可能・否定・義務の照合**: 評価用に試す。文の対応付けと作用範囲が難所であり、本体実装を急がない。
4. 条件や定量的根拠の確認は文脈を含む評価へ回す。ダッシュ挿入句は1軸目の局所候補として残すが、上記より後にする。

評価は「AI文を当てたか」でなく「指摘が必要な文を示し、自然な文を守れたか」で行う。手順書、README、報告書、議事録、エッセイを分け、引用・否定・時制・入れ子の対照例を含める。ルール調整用と未使用の確認用を分け、対応不能な入力も記録する。

正例・対照例各20件は初期の動作確認には使えるが、低い誤検出率の証明には足りない。たとえば対照20件で誤検出ゼロでも、Wilson 95%上限は約16.1%となる。既存の評価基盤で区間を示し、ジャンルをまたぐ精度を小標本から主張しない。

実装時は既存のトークン化を一度だけ使い、基本形・活用・byte位置を保持する。局所照合と節単位の集計を分け、位置の出せない観測を無理にfindingにしない。公表するJSONを変える必要が生じた時点で、具体例と互換性を別途決める。

当初の検討では23文の形態素確認と1文書のoutline確認を行った。その後、説明予告の反復を`repeated_explanation_preview`として実装した。`tech + experimental`限定で、構文境界の正例5/5、対照例0/10を確認した（詳細は[校正記録](calibration.md)）。上の3回は実験的な採用閾値であり、一般文書での改善率や最適性は未評価。項目数の不一致、意味変化の照合、6軸スコアは未実装。#9・#13の誤検出修正とは区別する。
