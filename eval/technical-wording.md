# 技術文書の言い回しを形態素で検出する

2026-09-13。技術文書で読み直す箇所を示すための検出仕様と、形態素解析による候補の探し方を記録する。

## 採用の考え方

単語の出現だけで文章の品質や執筆者を判定しない。技術的な意味が伝わりにくい言い回しや、文の型の反復を、前後の文脈とともに確認する。

Suikoでは「技術文書を公開する前に、近くに続く同じ文の型を見つけ、必要な比較や書き手の声を保って読み直したい」という利用場面を採用判断の軸にした。状況の中で利用者が進めたいことを捉える[Jobs to Be Doneの考え方](https://www.christenseninstitute.org/theory/jobs-to-be-done/)を、この用途へ当てはめた設計上の判断である。利用者へのインタビューで確定したジョブではない。

`repeated_distinction`と`repeated_em_dash`は`--genre tech`の通常検出に正式採用した。対象行をまとめて見直す作業を助ける`info`であり、表現の誤りや説明不足は断定しない。比喩の追加分は`--genre tech --experimental`に残す。いずれも自動修正は付けず、必要な表現は理由付きの`allow`で残せる。

## 検出候補と今回の対応

近接した反復の検出と、意味の曖昧さの推定を分ける。通常検出への採用は利用場面への適合によるもので、文章の改善効果を実証したという意味ではない。

| 候補 | 対応 | 読み直す観点・採用条件 |
|---|---|---|
| 気づきにくい失敗の比喩 | `technical_jargon_metaphor`を拡張 | 技術対象の直後に、静けさ・無言を表す修飾句と失敗・破棄の動作がある。通知やログの有無を説明できるか確認する |
| 効果をぼかす修飾 | 同カテゴリを拡張 | 技術対象について `地味に` と基本形 `効く` が隣接する。改善する対象や条件を確認する |
| 時間の消費を表す比喩 | 同カテゴリを拡張 | `時間を` と基本形 `溶かす` が隣接する。何に時間を費やしたかを確認する |
| 判断の方向を表す比喩 | 同カテゴリを拡張 | 技術対象について `安全側に` または `保守側に` と基本形 `倒す` が隣接する。選んだ設定・動作を確認する |
| 場所・配役による役割説明 | `abstract_metaphor`を拡張 | 抽象名詞に修飾された `入口`・`主役`、または抽象的な対象について述語として使った場合。既存の土台等の判定を再利用する |
| 違いを断定して締める反復 | `repeated_distinction`を正式採用 | 同じ節の5文以内に`別物だ／です／である`で終わる文が3文以上。比較の説明と文末の続き方をまとめて見直す |
| ダッシュによる接続の反復 | `repeated_em_dash`を正式採用 | 同じ節の5文以内に`—`・`―`を文中で使う散文が3文以上。1文の複数ダッシュは1文と数え、区切り方を見直す |
| 太字、箇条書き、定型見出し | 既存の検出を利用 | `high_bold_density`、`high_bullet_ratio`、`boilerplate_heading`など |
| 見出しの絵文字 | 追加を保留 | 装飾と意味のある状態表示を分ける評価例が必要。本文全体の記号密度と箇条書き先頭の絵文字は既存ルールにある |
| 時点を強調する表現 | 追加を保留 | 動作の過去形に続く時間名詞は形態素で抽出できるが、実際の状態遷移や測定時点にも普通に使う |
| 評価名詞で締める文 | 追加を保留 | 定番・定石・要点などの名詞と断定の文末を抽出し、反復を調べられる。ただし妥当な説明との区別を先に評価する |
| ほかの役割名詞・作業の比喩 | 追加を保留 | 道具・核心・構図や、潰す・踏み込む等は目的語と一緒に採取する。単語リストの拡張だけでは本来の用法も拾う |
| 検証・失敗・設定を表す一般語 | 禁止語には追加しない | 実測、照合、既定、事故などの有用性は、出現だけでは判断できない |
| 長い記事、読点、文長、多様な語彙 | 警告の追加・強化を保留 | 長さや読みやすさの観測値と、個々の文章の問題を分ける。読点や文長の既存レーンを使う |

## 形態素解析で候補を見つける手順

Sudachiは分割、品詞付与、表記の正規化を行う。分割モードによって複合語の単位が変わるため、Suikoが使うMode Cで結果を確かめる。[Sudachi公式の機能説明](https://github.com/WorksApplications/Sudachi#features)、[sudachi.rsの分割例と出力項目](https://github.com/WorksApplications/sudachi.rs#example)を参照した。

今回の実測環境は、Suikoが埋め込むsudachi.rs 0.6.11、SudachiDict core 20260723、Mode C。辞書や分割モードを変えたときは、トークン数や複合語の分かれ方を再確認する。

1. **候補句と紛らわしい例を対にする。** 失敗の説明なら技術対象と人間の動作、役割の比喩なら抽象的な設計と実際の建物を並べ、テスト用の文を作る。
2. **既存のMarkdownマスクを通して文を分ける。** コード、引用、見出し、箇条書き、表、参考文献等は今回の散文検出に含めない。マスクが残すbyte位置を使う。
3. **表層・基本形・品詞・活用形を同時に見る。** `surface`だけでは活用を取りこぼす。動詞の照合は`dictionary_form()`、品詞は`pos(0)`、サ変可能は`pos(2)`、活用形は`pos(5)`で確認できる。表記揺れを扱う`normalized()`と基本形を混同しない。
4. **助詞と隣接関係で範囲を絞る。** 文内に候補語が二つあるだけでは結び付けない。直近の対象、短い修飾句、動作の順を確認する。形態素解析は係り受けを確定しないので、別の主語や句読点をまたいだ候補は保守的に落とす。
5. **文末まで見て反復を集約する。** 名詞の出現数ではなく、所定の断定で終わる文の数を数える。疑問、否定、引用への接続、名詞修飾を分ける。
6. **元の文章の範囲を返す。** `byte_start`・`byte_end`から`TokenizedSentence::span`で元の行へ戻す。正規化後の文字列の長さから位置を作らない。

実装は [morph.rs](../src/lint/morph.rs) の `technical_wording_start`、`technical_repetition_findings`、`abstract_metaphor_findings`。形態素列と反例を繰り返し確認する入口は [technical_wording.rs](../tests/technical_wording.rs) にある。

```sh
# 実際の表層・基本形・品詞・活用形を表示し、同時に検出と位置を検証する
rtk proxy cargo test --locked --test technical_wording \
  technical_wording_detects_context_and_inflections -- --nocapture
```

## 実際に得られた分割と照合条件

以下は自作のテスト文をSuikoの辞書で解析した結果。品詞は判定に関係する項目を抜粋している。

| 入力中の部分 | 実際の分割・基本形 | 実装での注意 |
|---|---|---|
| `静かに壊れます` | `静か`〔形状詞〕 / `に`〔助動詞、基本形だ、連用形-ニ〕 / `壊れ`〔動詞、壊れる〕 / `ます` | `に`を格助詞に限定しない。壊れるの活用は基本形で拾う |
| `黙って捨てられた` | `黙っ`〔動詞、黙る〕 / `て`〔接続助詞〕 / `捨て`〔動詞、捨てる〕 / `られ` / `た` | 黙る自体を警告せず、修飾句の直後に破棄動作がある場合を拾う |
| `黙って無視される` | `黙っ` / `て` / `無視`〔名詞、サ変可能〕 / `さ`〔動詞、する〕 / `れる` | 無視の直後に基本形するが必要。無視リストという名詞は対象外 |
| `地味に効いてくる` | `地味`〔形状詞〕 / `に`〔助動詞、だ〕 / `効い`〔動詞、効く〕 / `て` / `くる` | 薬などの効能を避けるため、直近の対象を技術名詞に限定する |
| `時間を溶かしました` | `時間`〔名詞、助数詞可能〕 / `を`〔格助詞〕 / `溶かし`〔動詞、溶かす〕 / `まし` / `た` | 時間は抽象的な消費対象として限定できるので、技術対象の追加条件は課さない |
| `安全側に倒した` | `安全`〔名詞、形状詞可能〕 / `側`〔名詞〕 / `に`〔格助詞〕 / `倒し`〔動詞、倒す〕 / `た` | 安全側を一語と決め付けない。保守側も同じ分割で照合できた |
| `設計の入口として` | `設計`〔名詞、サ変可能〕 / `の`〔格助詞〕 / `入口`〔名詞〕 / `と` / `し` / `て` | 直前の抽象名詞と「の」を確認する。会場の入口は拾わない |
| `運用の主役は` | `運用`〔名詞、サ変可能〕 / `の`〔格助詞〕 / `主役`〔名詞〕 / `は` | 抽象名詞の範囲を既存の候補群と共有する |

短い修飾句には、表層の完全一致とトークン開始位置を併用した。これで活用語尾を列挙せずに済み、複合語の途中だけが偶然一致することも防げる。`時間を溶かす`の「を」は修飾句に含める。新しい用例へ広げる際は、語順や挿入語ごとに反例を追加してから条件を変える。

「失敗する／無視する」は名詞に続く基本形`する`を確認する。「壊れる／捨てる／効く／溶かす／倒す」は動詞の基本形で照合する。前後の助動詞は削除しないため、過去・否定・受身の表現にも自動修正を付けない。

技術対象は、修飾句より前の直近の `名詞＋は／が／を／も` を見る。最大12組の隣接トークンを後ろ向きに調べ、記号・空白・別の動詞で止める。設定や入力などの限定した技術名詞を対象とし、`設定を確認した人が黙って捨てる`は直近の主語が人なので除外する。これは係り受け解析の代用となる狭い条件であり、長い修飾を含む全表現の検出は狙っていない。

`別物`は名詞であることと、その後が`だ`・`です`・`である`だけで文が終わることを確認する。強調の`*`・`_`は文末判定で読み飛ばす。疑問符付きの文、`ではない`、`だと説明した`、`の資料`は数えない。

ダッシュは形態素の分かれ方に依存させず、マスク後の文の文字列を調べる。U+2014とU+2015の連続を一つのまとまりとし、両側の空白と強調記号を除いて文字または数字がある場合だけ候補にする。数字同士の範囲、ハイフン、長音記号、en dash、単独の罫線は除外する。対になったダッシュを含む1文だけで、反復閾値へ達することはない。

両カテゴリとも、候補の文番号を3件ずつ見て最初と最後が5文以内か確認し、その間にMarkdownの見出しがない場合だけ残す。見出し判定にも既存マスクを通すため、コード内の`#`は区切りにならない。文字・数字を含まない記号だけの文は距離に数えない。重なった範囲の候補を重複させず、カテゴリごとに1件へまとめる。`related_lines`にはその範囲の対象行だけを返す。見出しなしの話題転換、句点を含む引用内の文分割などは既存の文分割に従う近似である。

## 有効性の確認方法と限界

[確認前](../tests/fixtures/technical-wording-before.md)と[具体化後](../tests/fixtures/technical-wording-after.md)は、検出の用途を確認するための自作文。具体化後の記述は架空の仕様で、実際の推敲では著者が観測した内容に合わせる必要がある。単語の削除だけで解決としない。

```sh
rtk cargo test --locked --test technical_wording
rtk cargo run --locked --features evaluation --bin suiko-eval -- \
  labeled eval/technical-wording.toml
rtk cargo run --locked --features evaluation --bin suiko-eval -- \
  report eval/corpus.toml --split dev --external --experimental
```

新しいパターンのテストでは、活用、自然な近接例、別の対象、Markdownマスク、同じ行の複数文、Unicodeの列位置、反復の閾値、ジャンル、設定による無効化、終了コード、baselineの継続判定を確認する。反復の最初の文末やダッシュの種類が変わっても、同じ反復状態が残る場合はbaselineで継続扱いする。

専用のラベル付き評価は自作10文書・24項目で、全項目が期待どおりだった（manifestのSHA-256接頭辞`fa9b7b5a93f7`）。反復2カテゴリは各fire 5/5、silent 0/5。密集、強調、5文の境界、コード内の見出し、離れた説明、章ごとの比較、引用、数値範囲を確認する。同じ文書を複数カテゴリで使っており、24個の独立標本ではない。silentのWilson 95%上限は43.4%なので、一般的な誤検出率の小ささを保証する結果でもない。

2026-09-13の既存dev評価は人間ラベル75文書、AIラベル4文書。追加分が有効な技術ジャンルに限ると、それぞれ35文書、1文書だった。対象の4カテゴリはいずれも人間0/35、AI0/1で発火せず、この集合での新たな指摘は観測されなかった。ただし人間側のWilson 95%上限は9.9%であり、誤検出の少なさを保証できる規模ではない。AI側も検出0件なので、実用上の検出力を示す結果にはなっていない。評価manifestのSHA-256接頭辞は`95fb4f9cccb5`で、外部本文は既存lockとの一致を確認した。

近接条件を固定した後、holdoutを一度評価した。全20文書が人間ラベルで、技術ジャンルは10文書。対象4カテゴリはいずれも0/10、Wilson 95%上限は27.8%だった。この結果で閾値を調整していない。holdoutにも検出すべき反復のラベルはなく、指摘が増えなかった確認に限られる。

## 実文書での追加点検

候補語句で検索して得た公開13文書の本文を読み、同じ本文に変更前後の検出器を適用した。検索で候補を集めたストレス確認であり、無作為抽出でも人間・AIの分類用集合でもない。本文、取得元、本文のSHA-256、検出JSONはローカルの検証記録に保存し、外部本文は同梱しない。判定は実装担当AIの目視によるもので、2名以上の人間による独立評価ではない。

| 確認対象 | 観測した結果 | 採否への反映 |
|---|---|---|
| 時間の消費 | 4文書で5件一致したが、作業内容やつまずきは前後に説明されていた | 体験の語りを変える指摘になり得るため、正式採用しない |
| 気づきにくい失敗 | 2文書中1文書で1件一致。例外を握りつぶすコードの説明と意図的な擬人化があった | 表現の一致だけで説明不足とは言えず、実験機能に留める |
| 効果・判断の方向 | 各2文書で一致なし。省略された対象、候補外の名詞、挿入句があった | 検出なしを有効性の証拠にせず、文脈を広く拾う変更も見送る |
| 役割の説明 | 1文書で2件一致。後工程へ渡すデータと確認項目はすでに説明されていた | 自然な役割説明も拾うため、実験機能に留める |
| 文末・ダッシュ | 用語説明と障害記録を含めて確認。変更前のダッシュ2件は文書全体に分散した用例の合算だった | 同じ節の5文以内に限定すると2件とも出なくなった。太字による見落としも回帰テストで修正した |

対象4カテゴリの合計は変更前10件、変更後の実験モード8件、通常モード0件。変更後も残る8件は比喩の確認候補である。0件という結果は、新しい通常検出がこの集合へ追加の指摘を出さなかったという観測に限る。実際に直すべき反復をどれだけ拾えるかは、この集合だけでは評価できない。

正式採用する2機能のジョブは「局所的な反復箇所を探してまとめて読み直すこと」。検出位置と範囲はテストで確かめたが、文章の改善率や編集時間の短縮は未測定である。[評価手順](annotation-guide.md)が認める`info`確認候補として導入し、統計的な性能基準や人手評価を満たしたとは扱わない。自動修正や`warn`以上への昇格には、文書の目的を含む独立した人手評価が必要になる。

対象は散文で、見出し・箇条書き内の同じ言い回しは検出しない。技術対象の省略、コード表記だけの主語、候補にない複合語、句読点を挟む言い回しも拾えない場合がある。
