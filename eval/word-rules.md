# 形態素ルールの追加と短い主題の読点

2026-09-14。[p1ass/textlint-rule-preset-ai-words-ja](https://github.com/p1ass/textlint-rule-preset-ai-words-ja/tree/4de09b3467c48519595e941cf460ed4820a7be75) v1.2.0を調べ、Suikoで読み直す作業に役立つ機能を選んだ。対象はコミット`4de09b3467c48519595e941cf460ed4820a7be75`の実装、設定例、テスト。コードと語彙辞書を一括移植するものではない。

## 比較と採用判断

| 調べた機能 | Suikoでの対応 | 判断の理由 |
|---|---|---|
| 基本形・品詞・表層を組み合わせた形態素列の照合 | プロジェクト設定の`word_rules`を追加 | 「プロジェクト固有の曖昧な言い回しを、活用形も含めて探したい」という作業に使える |
| 独自辞書の追加・置換 | `.suiko.toml`へ独自ルールを追加。内蔵ルールの無効化は既存の`disabled_rules`を使う | 設定を一か所で管理し、読み込むファイルの探索や別の辞書形式を増やさない |
| 許可する表現 | 既存の`allow`を再利用し、独自ルールを絞る`rule_id`を追加 | 同じ抜粋に一致した別のルールまで抑制せず、残す理由を記録できる |
| 許可条件の正規表現 | 今回は追加しない | 現在の用途はIDと抜粋の部分一致で指定できる。必要な用例と誤抑制の確認が先になる |
| 短い主題の直後の読点 | `--experimental`の`short_topic_comma`を追加 | 文頭の区切りを見直す候補として位置を示せる。読点を取るべきかは文脈による |
| 読点検出の`maxLength` | 上流の既定値と同じ5文字に固定 | 閾値を増やす評価根拠はない。長い主題や動詞を含む節を除く |
| 一般語を含む単語辞書 | 一括での追加は見送る | 「検査」「実測」「照合」等は具体的な説明でも必要になる。上流テストにも、交通・建築・工具などの本来の用法に一致する例が明記されている |
| 技術現場の比喩 | 既存の限定した形態素検出を継続 | 「静かに壊れる」等は`technical_jargon_metaphor`、「土台」「入口」等は`abstract_metaphor`で文脈を絞って扱っている |

上流の[単語ルール](https://github.com/p1ass/textlint-rule-preset-ai-words-ja/blob/4de09b3467c48519595e941cf460ed4820a7be75/src/rules/no-ai-words.ts)と[テスト](https://github.com/p1ass/textlint-rule-preset-ai-words-ja/blob/4de09b3467c48519595e941cf460ed4820a7be75/test/no-ai-words.test.ts)、[読点ルール](https://github.com/p1ass/textlint-rule-preset-ai-words-ja/blob/4de09b3467c48519595e941cf460ed4820a7be75/src/rules/no-short-topic-comma.ts)を参照した。上流でも読点ルールは既定で無効になっている。

独自ルールの正式採用は、書き手が自分の編集方針を機械的に確認できることを理由とする。特定の語を使う文章の品質を判定するものではなく、利用者への取材や文章改善率の測定に基づく判断でもない。

## 独自ルールの形態素と位置

Suikoはsudachi.rs 0.6.11、SudachiDict core 20260723、Mode Cを使う。上流のKuromojiとは品詞体系や複合語の分割が異なるため、辞書ファイルの互換性は持たせない。上流の`basic_form`等をそのまま書くと設定エラーになる。

```toml
version = 1

[[word_rules]]
id = "value-change"
message = "増減・変更・移動のどれを指すか確認してください。"
tokens = [
    { surface = "値", pos = "名詞" },
    { surface = "を", pos = "助詞" },
    { dictionary_form = "動かす", pos = "動詞" },
]
```

実際の分割を使ったテストでは、「値を動かしました」は`値 / を / 動かし / まし / た`となり、「動かし」の基本形`動かす`で照合できる。「値を動かさない」も基本形で一致する。否定や過去を含めた読み直し候補なので、単純な置換は付けない。`surface`だけの照合と違い、活用形を列挙する必要がない。

各トークンの`surface`、`dictionary_form`、`pos`は任意だが、少なくとも一つが必要になる。複数指定した条件はANDで照合する。`pos`は「名詞」「動詞」「助詞」などSudachiの品詞大分類で、細分類や活用型、正規化表記は今回の設定に含めない。未知のキーや品詞、空の条件、重複ID、空のメッセージは受け付けない。

照合前に既存のMarkdownマスクと文分割を通す。指定された数のトークンが隣接し、すべての条件に一致したときだけ報告する。文・改行・空白・マスク箇所をまたぐ一致を作らない。「値札を動かした」「サーバーを動かした」「値を少し動かした」は上のルールに一致しない。コードの後ろに続く本文も、元の行のbyte位置から抜粋とUnicodeの列位置を作る。

結果は既存の`findings`へ`category: "custom_wording/value-change"`、指定メッセージ、重要度、原文範囲を追加する。未指定の重要度は`info`。IDを含むカテゴリで件数を集計し、`--fail-on`、GitHub注釈、SARIFにも反映する。前回比較はカテゴリと抜粋を照合するため、同じ文に一致した別のルールを混同しない。IDや条件を変えて比較すれば、その設定変更も結果に含まれる。

`allow`にIDを添えると、そのルールだけを許可できる。

```toml
[[allow]]
category = "custom_wording"
rule_id = "value-change"
text = "値を動かし"
reason = "直前で変更量を説明している"
```

IDを省略した`allow`は、従来どおりカテゴリと抜粋で照合する。`disabled_rules = ["custom_wording"]`は独自ルール全体を無効にする。個別ルールを使わなくなった場合はその定義と、そのIDを指定した許可を取り除く。通常の設定に独自ルールがなければ追加の形態素解析を行わない。

## 短い主題の読点

文頭から「は」までがUnicode scalarで5文字以内で、名詞句の直後に係助詞「は」と読点「、」がある場合を対象にする。読点の後ろにも内容語が必要で、改行と既存の文区切りごとに数え直す。動詞を含む節、引用符やコードから始まる文、長い主題は除く。「要点は、三つです」「この値は、固定です」は一致し、「読むのは、明日にします」「入力ファイルは、JSONです」は一致しない。

`span`は読点一文字を指し、`excerpt`には短い主題も入れる。通常の診断は変えず、`--experimental`でだけ`info`を出す。読点を取る提案は自動適用しない。意図した間や対比に必要な読点は、そのまま残す。`allow`、`disabled_rules`、前回比較、`--fail-on info`に対応する。

## 検証結果と限界

[回帰テスト](../tests/word_rules.rs)では、活用、全条件の一致、同じ行の複数箇所、絵文字後の列位置、コードと改行の境界、設定エラー、複数ファイル、JSON・CI出力、重要度、ID別の個別許可・前回比較を確認した。変更前には独自設定が未知のキーとして拒否され、読点の指摘も出ないことを失敗するテストで確認してから実装した。

既存の自作フィクスチャは、通常の診断が従来の19件と0件を維持する。実験モードでは、対照用の文書の「この事実は、」に新たな1件が出て28件から29件になる。もう一方の文書は0件のまま。これらは仕様を固定する自作文であり、実際の文章に対する精度の推定には使わない。

2026-09-14に、既存の開発用集合（人間ラベル75文書・AIラベル4文書）で確認した。manifestのSHA-256接頭辞は`95fb4f9cccb5`。外部本文は既存lockと照合し、今回holdoutは評価していない。独自ルールはCLIのプロジェクト設定なので、このコーパス評価では適用しない。

| 人間ラベルの範囲 | 読点が一致した文書 | 一致した箇所 |
|---|---:|---:|
| essay | 7 / 18 | 12 |
| tech | 12 / 35 | 31 |
| business | 15 / 22 | 104 |
| 合計 | 34 / 75 | 147 |

これは短い主題の読点の出現状況であり、147箇所を誤りと判定した結果ではない。人間文書にも広く現れることが分かったため、既定で有効にしたり、`warn`へ上げたりする根拠にしない。通常モードでは追加の読点指摘は0件だった。AI側は4文書しかなく、執筆者を判別する性能の根拠にはできない。

独自ルールの有効性は、登録する条件とそのプロジェクトの編集方針に依存する。読点の削除による読みやすさ、文章の改善率、編集時間の短縮は未測定。形式が一致したことと、直す価値があることを区別して使う。

```sh
cargo +1.97 test --locked --test word_rules --test compatibility
cargo +1.97 run --locked --features evaluation --bin suiko-eval -- \
  report eval/corpus.toml --split dev --external --experimental
```

両機能はv0.3.7で追加した。設定形式は`version = 1`に任意の`word_rules`を追加し、既存の設定は引き続き読める。独自ルールのIDは`category`に含め、既存ルールのJSONとRust公開型`Finding`のフィールドは変わらない。既存フィールドでの構築とJSON出力を互換性テストで確認した。旧版のbaselineはバージョンの照合で拒否されるため、v0.3.7で作り直す必要がある。
