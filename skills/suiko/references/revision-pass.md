# 既定の推敲手順

短い文でも、追加モードの指定がなくても行う。本文の修正を求められたら、指摘一覧や言い換えの候補だけで終えない。診断だけの依頼と、本文のみを返す指定は優先する。

## 1. 原文と用件を把握する

全文を読む。原文、依頼、提供資料、利用者が示した文脈を区別し、原文の控えを残す。自分が前に推測した説明を根拠として使わない。新規執筆なら資料と依頼を出発点にする。

誰が誰に何を伝える文書か、文書の用途、読み手、常体・敬体、指定された見出し・長さ・書式を確認する。不明な設定は推測で固定しない。[用途ごとの扱い](revision-context.md)に従う。

技術文書では[技術文書の推敲](technical-revision.md)を使う。仕様や操作を曖昧にする表現は、資料で確かめた動作へ直す。エッセイの語りや、技術記事の個人的な体験まで説明文へ均さない。

段落ごとに話題と前段との関係を把握する。各文について、主体・相手・対象・動作、条件と例外、否定、時期、確度、文の働きを読み取る。事実、意見・評価、依頼・決まり、比喩、皮肉・冗談、仮定・予測、引用・伝聞を混同しない。メモを完成文へ混ぜない。

## 2. 意味の対応を直す

次の点を検出の有無にかかわらず全文で確かめる。

| 確かめる関係 | 直し方 | 残す条件 |
|---|---|---|
| 主語と述語 | 動作の名詞を、必要なら「〜するには」へ開く。使役は誰が誰にさせるかを保つ | 主語を推測で足す必要があるなら原文を残す |
| 主題と後半の節 | 「〜は／では」の話がどこまで続くかを確かめ、別の主体への切替が明らかならその主体を示す | 同じ部品内の処理か別の設定か不明なら、場所や主体を作らない |
| 他動詞と目的語 | 挟まった比較や条件の後でも何を扱うか追えるよう、前後に明示された対象を再掲する | 近くにある名詞というだけで選ばない。対象不明なら動作の名詞を主題にする案も検討する |
| 修飾・条件・並列 | どの動作・名詞に掛かるかを保って語順や文を分ける | 「独立した展示」を「独立して担当する」のように、名詞の性質を行為へ移さない |
| 操作と結果 | 操作ごとに、残るもの・変わるもの・次に行うことを対応させる | 失敗時に代入しない処理をfalse代入へ変えない。未定義の状態を埋めない |

例: 「ログの一括削除は、保存先の権限も変える必要がある」は「ログを一括で削除するには、保存先の権限も変える必要がある」とできる。必要性は保ち、実施済みや単なる推奨へ変えない。

「処理は設定を読み込み、集計だけを担当させる」は、使役の対象がその処理だと確定していれば「処理には設定を読み込ませ、集計だけを担当させる」とできる。主語の省略を直すために、別の動詞や主体を作らない。

## 3. 論理と読み順を整える

接続詞、主題の「も」、指示語が何と何をつなぐか確かめる。「そこで」「そのため」を、関係が不明な箇所へ便利なつなぎとして足さない。見出し・問い・列挙の導入と、実際の項目・結びが対応するかも読む。

一段落に異なる話題が混ざる場合は、原文の順序と関係を保って分ける。条件と動作、理由と結論の途中では分けない。句点ごとの改行、全段落の長さ合わせ、空行の一律追加はしない。

予告だけの文は、評価を残して後続の内容へまとめられるか考える。項目数の宣言と実数が違う場合は、数や項目を勝手に増減しない。読み手の案内になる予告、長文の要約、指定されたまとめ、報告の次の予定は残す。削るときは、その箇所だけにある条件・値・例外を落とさない。

漢語を助詞なしで詰めた句は、「設定変更後」→「設定を変更したあと」のように関係を開く。定着した複合語と正式な項目名は保つ。「とき」が続いてかえって読みにくくなるなら、元の「時」「際」も使える。

## 4. 文末と語彙を整える

文ごとに説明・依頼・助言・決まり・予定・実施済みの報告を区別する。現在の仕様を今回の変更へ、完了報告を予定へ変えない。助言文書に含まれる道具の動作説明は、説明のまま残す。敬体・常体の変更と、文の働きの変更を分ける。

許可、能力、義務、保証は互いに置き換えない。「含めてよい」→「含められる」は不可。「することができる」→「できる」は可能を保てるが、実感を述べる「今月も計画どおりに進めることができました」は、単なる完了へ縮めない。

[表現別の修正判断](revision-catalog.md)を使って、比喩・擬人化・直訳語・名詞化・セルフラベル・否定対比・コピー調・装飾・補助動詞を確認する。各候補に対し、読みづらさを直す案を作り、次の5項目を照合してから採る。

修正案を採る前に、何が読みづらかったのかを原文で確かめる。検出語やカタログに当たることだけでは理由にしない。
意味の通じる体験の比喩・後悔・実感を、一般的な報告表現へ均さない。

1. 主張、論点、評価の向きと比重が同じか。
2. 動作主・相手・対象と、文の働きが同じか。
3. 否定、条件、例外、限定の範囲が同じか。
4. 確度、時制、伝聞、気持ちの含みが同じか。
5. 数値・単位・名称・識別子・時期が同じか。

変わる案は採らない。意味が読み取れないことを批評する文や「〜とされている」へ逃がさず、元の主張を本文に残す。確認は本文の外へ分ける。意図的な曖昧さを一つの読みへ狭めない。

## 5. 修正後の本文を照合して渡す

原文の`suiko lint`を修正の手掛かりにし、最終稿には`suiko check`を実行する。原文を`--before`、提供資料を`--material`へ渡す。指摘の増減を追う場合は同じ設定のbaselineも使える。検出をゼロにするための書き換えはしない。文の言い換えはSkillを実行するエージェントが候補を判断して編集する。太字の書式だけは、利用できる版の`fix --bold`でプレビューし、修正の依頼範囲内なら`--write`で保存できる。保存後も原文との差分を確認する。

変更した箇所を原文から最終稿へ読み、消えた条件や否定を確かめる。最終稿から原文・資料へ戻り、追加した主体・相手・数値・因果・気持ち・約束の根拠を確かめる。前からある未定・調査中・未確認を、確定・完了・影響なしへ変えない。短くなっても名詞化で硬くなっていれば、自然な動詞へ戻す。

[資料照合](revision-context.md#資料との照合)では、値が登場するだけでなく、対象・単位・時点・条件との組を比べる。資料から追加した事実があれば出所と追加した内容を報告する。資料の不足と、原文そのものの未定を区別する。

最終稿に対する検査を終えた後に本文を変更したら`check`をやり直し、提出前に`verify`で記録との一致を確認する。原文・資料・設定が変わった場合も再検査する。CLIが古い場合は利用できる`lint`・`diff`と読み合わせで進め、記録・再確認の未実施を伝える。検査記録と入力の控えは、再確認が必要な間は一緒に保管する。最終稿、実際の変更点、重要な確認事項を渡す。本文のみの指定では本文だけを返す。「直した」と報告するのは実際に採った変更だけにする。
