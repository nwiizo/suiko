# 技術文書の推敲

技術解説、仕様、手順、障害報告、技術的なPR説明では、追加指定を待たずにこの方針を使い、CLIには`--genre tech`を渡す。エッセイへ同じ説明量や言い換えを要求しない。

## 動作と条件を読める文へ直す

本文だけでなく見出し・箇条書き・表も読む。読み手が実装や操作を取り違える箇所は、意味が通るという理由だけで残さない。原文と資料で確定できる対象・動作・条件を使って修正する。既知の専門用語、正式名称、コード、識別子は保つ。

| 原文の型 | 修正の方向 | 保つもの |
|---|---|---|
| ログの採取は、出力先を指定する必要があります | ログを採取するには、出力先を指定する必要があります | 必要条件。実施済みや単なる推奨へ変えない |
| 結果の確かめを実施します | 結果を確かめます／結果を確認します | 対象と動作。「確認」を硬い語という理由で避けない |
| 設定変更後に実行します | 設定を変更したあとに実行します | 変更と実行の順序。正式な項目名は維持 |
| エラーを握りつぶします | 資料にあるエラーの扱いを具体的に書く | 戻り値、通知、ログ、処理の継続は別々に確認。記載がなければ推測しない |
| 処理を別スレッドに逃がします | 別スレッドで処理します | 非同期化、並列数、待機の有無を勝手に補わない |

比喩が動作説明を代わりに担っている場合は、根拠のある動作へ直す。技術記事に含まれる本人の後悔や経験、文脈から意味が通じる余談まで一律に書き換えない。

`evaluative_ability_past`は体験を述べる候補であり、短縮の命令ではない。「楽しく読書を進めることができました」は実感を残し、「旧版では取得することができました」は機能と時制を保って縮められるかを読む。可能動詞の`review_suggestion`は`suggestion`と区別し、主語・能力・受身・確度を確認してから採る。

短い主題の直後でも、唯一の読点、後続の別主語や長い修飾節との区切りは残す。削除後に読解負荷や太字の表示が悪化しないことを確認する。`**`の前後だけを正規表現で一括変更せず、開きと閉じを確認する。コードのコメントは本文と一緒に置換しない。装飾の空白は必要な文字側だけへ置き、句読点・括弧の外側へ増やさない。

`word_usage`は誤用の候補を文脈から確認するために使う。主述関係・述語句の反復・段落の文体混在はtechの`--experimental`で試せるが、通常の推敲の前提にはしない。技術文書の見出しの絵文字や不可視文字も、正式名称・必要な結合制御を一律に削除しない。

動詞の連用形に続く「ずらい」は、接尾辞だけを「づらい」へ直し、過去形などの活用を保つ。「使いずらかった→使いづらかった」が一例。引用や固有名の意図した表記は残す。可能形への縮約は形態素から候補を作れるが、「取れる」単独の語義や、受身・能力の区別まで確定するものではない。

太字の修正は、利用できる版では`fix <file> --bold`でプレビューする。明示したファイルの修正依頼なら`--write`で保存できる。コード・引用・リンク先の保持と残った候補は、保存後のlint・diffでも確認する。`duplicate_comma`は重複の位置を示すが、表記例や意図した間は残す。`low_specificity`が境界付近の場合、縮約で語数が変わっただけの可能性を読み比べ、情報や事実を作り足さない。`compare`の「新規」は現在は抜粋で対応づけるため、その件数だけで修正が文章を悪化させたと判断しない。

## 数値・役割・未確認事項を照合する

数値は対象、単位、測定指標、環境、時点と組にして読む。検証環境の中央値が900msから300msになった資料から、本番の性能やスループットを断定しない。「必ず」「安全」「改善」には、その範囲と根拠が必要である。

「削除してもよい」は許可、「削除できる」は能力、「削除する必要がある」は義務として区別する。担当者の判断が削除の条件でも、担当者が削除できるとは限らない。「失敗時は設定値を更新しない」を「失敗時はfalseを設定する」へ変えない。

未測定・未確認・未定・調査中は、そのまま伝えるべき情報である。資料と原文が食い違うときは、資料に基づく訂正が依頼の範囲に含まれるか確認し、表現の修正と事実の訂正を分けて扱う。

## 検査してから渡す

最終稿を保存し、`check`へ原文と実際に参照した資料を渡す。資料を推測で作らない。

```sh
suiko check final.md --before original.md --material source.md --genre tech --json
suiko verify final.md.suiko-check.json --json
```

資料が複数なら`--material`を繰り返す。原文がない新規執筆では`--before`を省く。資料のない改稿では`--material`を省き、資料照合を実施したと報告しない。検査記録と、その記録が参照する原文・資料は、再確認が必要な間は一緒に保管する。

`check`はlint・読解負荷・差分・資料照合をまとめて実行する。候補を読み、採用した修正があれば再実行する。提出前の`verify`は検査後の変更を確認する。`--replay`を付けると検査結果も再計算する。一致や候補0件を文章の合格判定にしない。CLIが古く`check`を使えない場合は、利用できる`lint`・`diff`と資料の読み合わせで仕上げ、記録・再確認が未実施であることを伝える。
